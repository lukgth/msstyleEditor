# Win7 -> Win10 importer, developer notes

Code: `libmsstyle/Import/`. CLI: `msstyleImport/`. UI: `MainWindow.OnImportWin7Style` plus the result window `msstyleEditorSharp/Dialogs/Win7ImportDialog.cs`. Tests: `libmsstyleTests/Win7ImportTests.cs`. Tests that need a third-party Windows 7 style (not redistributable, so not in the repo) read its path from an environment variable and are inconclusive without it.

The base (stock Windows 7 aero) is `libmsstyleTests/styles/w7_aero.msstyles`, embedded into libmsstyle as `libmsstyle.Import.w7_aero.msstyles`. `StockStyles.Win7AeroPath()` writes it to `%TEMP%\msstyleEditor\w7_aero-<sha>.msstyles` because `VisualStyle.Load` goes through LoadLibraryEx. It has no .mui next to it, so base font/string properties can only be compared by id: a source that rewrote the text behind an unchanged id isn't detected (noted in every report).

In the editor the template is the open style: it's saved (standalone) to `%TEMP%\msstyleEditor-import\<time>\template\`, so unsaved edits count, the import writes `...\out\<name>-win7import.msstyles`, and on success that file replaces the open style. On failure the open style is left alone.

## Pipeline

1. `VisualStyle.Load` all three; any `LoadDiagnostics` entry blocks the run. Platform must be Vista/7 for source and base, 10/11 for the template.
2. `SemanticModel` flattens each style to `class|part name|S<state>|property#type[@n]`. Images compare by decoded pixels, string ids (FONT and non-image FILENAME) by their string-table text when both sides have a table, by id otherwise. Only IMAGEFILE..IMAGEFILE7/GLYPHIMAGEFILE are IMAGE references; resource ids use the low word like uxtheme. Numeric class ids never take part in matching.
3. `BuildThreeWayDiff` records every key (written to `<prefix>.threeway.json`).
4. `DwmImport` handles DWMWindow (below), then `MergeGenericClasses` everything else.
5. New bytes go through `ResourceIdAllocator` (max id + 1, shared when bytes are identical; ids with several language variants are never shared). Existing resources are never rewritten.
6. `VisualStyle.Save` into a validation folder of its own, with `StyleCompanions.CopyAlongside` putting the template's `Shell` folder and `<lang>\<name>.msstyles.mui` next to it (mui-based templates only resolve their string tables that way), then `StyleValidator` against the template. On success the file is moved to the output and the companions are copied there too; the validation folder is always deleted. The editor passes the opened file as `CompanionSourcePath`, because its template is a temp snapshot.

## Merge rules

- Three-way: source == base -> keep template; template == base -> take source; template == source -> nothing; otherwise keep template (`--prefer-source` overrides).
- Colors (type COLOR) always follow the source, over template adaptations too (`applied-color`). A color the source deletes is deleted from the output (`removed-color`, `RemovedRecords`). Other removals aren't imported. The validator accepts exactly the declared removals.
- A removal never empties a class, and an addition never gives a record-less class its first record. uxtheme registers only classes that have VARIANT records and BCMAP parents index that registration order (see the binary evidence table), so emptying or filling a class shifts the parent of every later class: fonts and colors inherited through BCMAP then come from the wrong class (a tray flyout falling back to the System font is what that looks like). A class's last color instead gets the value the deletion falls back to (`pinned-color`). The validator checks that the classes with records, and the order they first show up in VARIANT, match the template.
- Records the source adds where stock Windows 7 has none (text glow on the address bar, a tree view font...) are added to the template (`added`, `TryAddRecord`) when the class exists there; a missing part/state section is created. The value goes through the same translation as any applied value.
- Template-only records that hide a value the source changed further up the inheritance chain get the source's value copied in, never deleted (`CopyIntoTemplateOverrides`, `copied-into-override`). Example: `Explorer::Button` doesn't exist on Windows 7, inherits `Button`, and adds its own PUSHBUTTON text colors that would otherwise beat the source's `Button` colors. Colors are copied in any class; other scalar types only in Windows 10-only classes. Pictures and strip geometry stay the template's. A Windows 10-only class also gets the source's other states of such a property where they differ from state 0 (`added-state-copy`), because Windows 10 falls back to the class's own state 0 there, not to the base class's state. `DarkMode*` classes are left alone: their dark backgrounds need the template's light text.
- Fonts are compared as parsed `FontSpec`s (grammar from uxtheme `_ParseFont`). A font the template has no string for is added to every string table with a fresh id and the candidate is saved standalone. The validator parses every font, checks all old strings still read the same and checks caption/small caption/menu fonts against their bar heights.

### Pictures and geometry

- Images that differ only by +-2 premultiplied rounding count as equal; templates often re-encode the stock images that way (real retouches differ by much more).
- When the template shows a stock picture that belongs to another part (e.g. a tab item drawn with the stock left-edge tab strip), the source's version of that other part is used (`FindImageAlias`, `applied-alias`).
- Strip geometry stays consistent: if IMAGECOUNT/IMAGELAYOUT/SIZINGMARGINS is a kept conflict, or the source changes one of them while some image of the part stays the template's, the whole part keeps the template geometry (`LockedGeometryParts`). Images on their own are decided one by one.
- A picture the template redrew (a conflict without a stock alias) takes the source's picture when the part ends up cut with the source's frame count, layout and margins (`GeometryIsSource`, `applied-picture-with-geometry`).
- Template-only dpi slots (IMAGEFILE1-7 the base doesn't have) don't lock a part. `FillDpiSlots` points them at the source's largest picture of the same state wherever the import replaced that state's pictures (`applied-dpi-fill`). Images both the source and the template added on top of stock follow the source in parts that take the source's geometry (`applied-with-geometry`).
- `PropagateImages` walks template images nobody touched (Windows 10-only classes, dark mode copies, extra dpi slots) that aren't still their own key's stock picture: a stock Windows 7 picture -> the source's version of it (`applied-stock-copy`), and an IMAGE id shared with an already replaced property -> the same replacement when all replacements of that id agree (`applied-shared-id`).
- XP sources only: Luna10 moved some stock pictures to another slot of the same part/state (TrayNotify buttons IMAGEFILE -> IMAGEFILE1, Combobox/Rebar chevron GLYPHIMAGEFILE -> IMAGEFILE1-7). `FollowMovedImages` gives such slots the source's version of the stock picture (`applied-moved-slot`).
- XP sources only: a geometry scalar the template retuned (SIZINGMARGINS) doesn't lock its part when every template picture there is still stock and the source replaced them; the source's numbers come with its pictures (TrayNotifyHoriz::TrayNotify). ExplorerBar is left to the shellstyle import.
- XP shellstyle bitmaps drawn with `rcbmp(id, 2, ...)` (per-pixel alpha) follow DirectUI's rule (`convert.cpp` `HasAlphaChannel`): any non-zero alpha byte means the alpha channel is used, so 0/255-only bitmaps (TangoLux's task pane arrows) keep their transparent pixels. The uxtheme rule (alpha only counts when some pixel is partial) turned their background white.
- XP shellstyle geometry: `sectionlist` padding becomes ExplorerBar part 0 CONTENTMARGINS (the Windows 10 UIFILE's `gtmar(ExplorerBar, 0, 0, 3602)`); a header button's borderthickness + padding difference from stock Luna is added to the vertical CONTENTMARGINS of NORMALGROUPHEAD/SPECIALGROUPHEAD, which the port fitted to stock Luna. Checked against TangoLux on a real XP: group header tops 7/121/255px in both.
- XP shellstyle values are looked up the way DirectUI cascades them, not under one fixed selector: a header's text and background come from its title element (`element [id=atom(title)]`) before the header button, and both fall back to the plain `element` rule every DUI class derives from; group fills go fill selector -> `tasklist` -> `element`. A one-color header bitmap becomes a flat header tile. Stock Luna sets everything on the button/tasklist, so its result is unchanged. Lion OS X sets its header text on the title and its fills on `element` only: its pane kept Luna10's white groups and blue header fades with white titles that couldn't be read.
- XP sources only: a BGTYPE the source changed but the template never had is added. uxtheme defaults a missing BGTYPE to BORDERFILL, which ignores the IMAGEFILE that does come over (TangoLux's address box lost its frame on Luna10's plain Combobox).
- XP sources only: IMAGELAYOUT/IMAGECOUNT records the template doesn't have are added from the source, and the strip-fit check uses the source's layout there. A missing IMAGELAYOUT is horizontal on XP but vertical on Windows 10, so Lion OS X's three side-by-side `TrayNotifyVert` tray frames (Luna10 dropped that part's layout) were rejected as "doesn't split into 3 vertical frames" and Luna's tray picture stayed.
- XP sources without `Shell\<scheme>\shellstyle.dll` (Flarn): XP's shell32 (`SHGetShellStyleHInstance`) falls back to `%SystemRoot%\System32\shellstyle.dll`, the classic stylesheet written in system color names (`window`, `buttonface`, `activecaption`...). That file (from XP x64 SP2, embedded as `xp_classic_shell.dll`) becomes the source shellstyle, its color names resolved with the theme's own SysMetrics (uxtheme's `DefaultColors` where the theme leaves one out). Measured on XP x64 SP2 under Flarn: the special group (System Tasks) is drawn like the other groups (buttonface header, buttontext), not activecaption as the stylesheet reads, so it takes the normal section's header/tile. Color headers become flat 10x10 tiles; bare `rcbmp(id)` arrows are color-keyed on their top-left pixel (DirectUI `GRAPHIC_TransColor` with an automatic key).
- XP sources only: an image glyph (`GLYPHIMAGEFILE`) is re-cut with the same frame map as its part's strip (Toolbar SPLITBUTTONDROPDOWN 6 -> 8), and the template's glyph dpi slots (IMAGEFILE1-7 of a part with GLYPHTYPE=IMAGEGLYPH and an IMAGESELECTTYPE) take the source's glyph, not its background strip. The back/forward dropdown arrows were missing before.
- The validator wants every changed strip image to divide into its effective IMAGECOUNT, except where the source ships that exact picture with that count: Windows 7 drew those and no uxtheme check rejecting a remainder was found, so they're warnings (`CollectFrameWaivers`). XP sources whose strip has the same count and layout as the target property are applied despite a remainder (uxtheme slices `length / count` on XP and Windows 10 alike) and get the same waiver: appows' 53px frame borders with ImageCount 2.
- XP bitmaps: a 16/24/32bpp DIB can still carry `biClrUsed` palette entries; the pixels start after them (GDI skips them). Reading from right after the header turned appows' separators and tree glyphs into palette garbage.
- XP strip re-cuts (`XpStripRemap.LearnMap`): a stock frame is a candidate for template frame j only if it matches in every comparable image of the state (background and glyph strips). Stock ScrollBar ARROWBTN backgrounds are identical for all directions, so the background alone mapped the down/left/right hover frames to "up"; the glyph strip disambiguates. Among candidates j itself wins. A part the template redrew takes the map of the part it's drawn on (ScrollBar GRIPPERHORZ/VERT <- THUMBBTNHORZ/VERT); Luna10's grippers are blue art.
- XP strip re-cuts where Luna10 also changed the frame size (Header HEADERITEM: 5 frames of 18x18 -> 12 of 18x20; ScrollBar ARROWBTN 15px -> 17px): stock frames are compared scaled to the template's frame size, and the re-cut stock is scaled the same way. The source's art keeps its own frame size; uxtheme stretches it by SIZINGMARGINS as XP did. Scaling it duplicated the middle row/column, which is where an arrow glyph sits (Flarn's scroll arrows came out fat).
- Strips where win10 added states xp never drew (Button CHECKBOX: 12 -> 20 frames, the last four are "excluded"): when at least three quarters of the template frames match stock, the rest take their closest stock frame (reported). The re-cut stock then becomes the template's own strip, so the importer sees stock the template left alone and the source's art replaces it, including the dpi slots Luna10 rescaled (CheckBox25 -> 20px). Before, Luna10's white boxes stayed under GSM.
- XP sources: ListView/TreeView/ListBox with a non-white BORDERFILL get SIZINGBORDERWIDTH 2. comctl32 `CCDrawNonClientTheme` (cutils.c) draws a client edge with the theme background, then fills what a BORDERSIZE thinner than the 2px edge leaves with the control's brush, which is white for Task Manager's, the Open dialog's and WinForms lists: a 1px white ring inside GSM's dark border.
- XP sources: Spin UP/DOWN/UPHORZ/DOWNHORZ pictures with transparent pixels are flattened onto the source's BTNFACE. comctl32's up-down erases with BTNFACE (updown.c class brush) before drawing them; WinForms' NumericUpDown buttons (`UpDownButtons`, `ControlStyles.Opaque`) don't, and GSM's fully see-through button backgrounds showed white.
- XP sources: a single source strip frame (GSM's shafts) is repeated into every template frame; a source strip with stock's frame count but the other layout (GSM's horizontal thumb strip) is cut in its own layout and mapped like stock.
- XP sources: one IMAGEFILE where the template picks its picture from IMAGEFILE1-7 (IMAGESELECTTYPE set) fills those slots (`SingleImageIntoDpiSlots`); uxtheme never reads IMAGEFILE there. `Explorer::TreeView` GLYPH/HOTGLYPH (no `TreeView` inheritance) take `TreeView` GLYPH: GSM's +/- boxes.
- XP sources: a COLOR the source changed that the template dropped is added (Luna10's Combobox has no FILLCOLOR; GSM's address box was white).
- XP sources: template pictures painting an area XP filled with a color become a borderless BORDERFILL in that color when the source changed it (`FillFlatFromXp`): Edit BACKGROUND <- Edit EDITTEXT FILLCOLOR (win10's themed edit paints EP_BACKGROUND first; the address bar and text boxes stayed white), PreviewPane NAVPANESIZER/READINGPANESIZER <- system BTNFACE (Luna10's beige 3px pane splitter).

## Windows 7 vs Windows 10 role changes

Some things Windows 7 drew from one record are drawn from another one on Windows 10. Inheritance can't express that, so `MirrorIntoWin10Classes` copies the source's effective value across (`applied-mirror`), only where the source changed it from stock. Dark-mode siblings are not mirrored. Each entry is marked verified (observed rendering or code) or inferred (role match plus matching stock values).

Shellstyle: the Windows 10 template's own shellstyle is already its Windows 10 port. A Windows 7 shellstyle can't be dropped into Windows 10 (Explorer fails to load it), so the importer never touches the `Shell` folder; the theme references that differ between the two shellstyles are covered by the table above. Other differences are hardcoded colors or Windows 10-only art with no Windows 7 data: the file dialog's bottom strip moved from `MenuStyle` part 13 to a `CommonItemsDialog` picture, plus the barrier page, library pane and infobar.

Not imported on purpose: plain dialog labels (e.g. drive Properties) that a dark Windows 7 style leaves black are black on Windows 7 as well; the importer doesn't invent colors for them.

Checking colors by hand: applying only the `.msstyles` (without a `.theme`) can leave the previous system palette active, so system-color controls look wrong on both systems. Apply a complete `.theme`. Windows 10 doesn't load a visual style's sysmetrics colors into win32k, so the XP `.theme` files carry them as `[Control Panel\Colors]` (`XpThemeFiles.SysColors`); without that appows ran with GSM's light-blue WINDOWTEXT.

## Color and size variants (XP)

uxtheme 19041, observed with `LoaderLoadTheme`/`EnumThemeColors`/`EnumThemeSize`/`GetThemeDocumentationProperty` on hand-edited copies of Luna10:

- `VMAP`: (VARIANT resource name, size name, color name) triples; each string is an int32 wchar count (terminator included) and the wchars, padded to 8 bytes. `LoaderLoadTheme(color, size)` picks the VARIANT resource of the matching triple (E_INVALIDARG for an unknown pair).
- `EnumThemeSize`/`EnumThemeColors(index)` walk the CMAP classes named `sizevariant.X` / `colorvariant.X` in CMAP order; the name is X, an index whose class has no VMAP triple fails (Luna10's `sizevariant.Default` is index 1, so a size added after it is index 2). Callers must skip failed indices.
- `RMAP`: 32-byte records (name id, type 201, class index, part, state, string id, 0, inline byte count) with an inline UTF-16 string or a string table id. 601 = display name, 602 = tooltip; class 0 (`documentation`) 601 is the theme's DisplayName.
- Records of a variant class are never needed; added classes go to the end of CMAP (no VARIANT class index moves) with a `-1` BCMAP entry.

`XpThemeImport` writes Luna/Olive/Silver's layout: one folder per theme, one `.msstyles` per color scheme named after the scheme, `Shell\<scheme>` next to it (Windows loads `Shell\<ColorName>\shellstyle.dll`; checked: Green loads `Shell\Green`). Each other XP size (`[File.X] Sizes = LargeFonts`) is ported on its own from the same template (`Win7ImportOptions.SourceSize`) and merged by `VariantWriter` as VARIANT `S_<SIZE>`: its IMAGE/STREAM resources and font strings are matched to the main file by content, new ones get fresh ids. The color variant is renamed to the scheme (`colorvariant.Green`, display name "Green") and the documentation name becomes the XP theme's. Every color/size pair is then loaded through uxtheme (`UxthemeLoader`); a failure blocks the scheme.

Names come from the packed XP style's string table, which is what XP itself showed (themeldr `tmutils.cpp` `_EnumThemeColors`/`_EnumThemeSizes`, `GetThemeDocumentationProperty`), not from THEMES_INI's `DisplayName` lines: color i = string 1000+i and size i = 3000+i (i = index in the `COLORNAMES`/`SIZENAMES` resources), theme name = 5000. Authors set these freely: Flarn's sizes are "HaxrCorp S8 / Tahoma / Trebuchet MS", appows' "segoe ui / corbel / arial", minus4's "[01/03] default ...". The default size's name goes onto the template's `sizevariant.NormalSize` class.

Color schemes come from packthem's tables, which is what XP loads: COMBODATA (`cColors, cSizes`, then the file number of every color/size pair, -1 = none; themeldr `tmutils.cpp` COMBOENTRY) indexes FILERESNAMES, COLORNAMES/SIZENAMES name them. THEMES_INI only supplies display names, and is only parsed for schemes when a style has no COMBODATA. Its `[File.X] ColorSchemes` lines can name schemes that don't exist: Lion OS X has `[ColorScheme.NormalColor]` but every file says `ColorSchemes = Lion`, which packthem resolved when it built the tables ("No color schemes found in THEMES_INI!" before).

deskn.cpl (`deskcpl`, AppearancePage.cpp), matched to XP's themeui (`nt5src/.../shell/themes/themeui/baseappearpg.cpp`): every folder directly in `Resources\Themes` is a "Windows and buttons" entry, labelled with its styles' documentation DisplayName (XP `CSkinScheme::get_DisplayName`); colors and sizes show EnumThemeColors/EnumThemeSizes `szDisplayName` as is (Luna/Olive/Silver keep their localized names). Apply with a size goes straight to `SetSystemVisualStyle(path, color, size)` with metrics built from that variant (Theme Manager ignores sizes). After every msstyle apply deskn sets and persists the style's 31 system colors, as XP's uxtheme did (`loader.cpp` SetSystemMetrics: `SetSysColors(TM_COLORCOUNT)` + `PersistSystemColors`); Windows 10 doesn't, and GSM "three" ran with the previous scheme's palette.

## DWMWindow

The template atlas has to be the stock Windows 7 atlas (pixel-compared, `TemplateAtlasIsStockWin7`). Then:

- a template rect equal to the stock rect of the same-named Windows 7 part maps by name;
- otherwise the rect is looked up among stock Windows 7 rects (alias). Several Windows 7 parts may share one stock rect; that's only followed if the source gave all of them the same pixels (`ChooseAlias`);
- anything else keeps the template sprite, copied into a strip below the source atlas (`fallback`), and the part keeps its template properties.

A mapped part takes the source sprite at whatever size it has, plus the numbers that describe it (IMAGECOUNT, SIZINGMARGINS, CONTENTMARGINS, `applied-with-sprite`), even where the template had adapted them: those belonged to the template's sprite. The fallback is only for sprites that can't be traced, or parts excluded by rule.

`CheckGeometry` then only warns (`GeometryWaivers`, `dwm-geometry-warning`). Strips are taken as sliced proportionally like the editor slices them (uDWM's rounding isn't verified), so odd sizes are fine; what gets a warning is a strip with nothing left after uDWM's 1px inset, or margins wider than the strip. Exclude rules work here too: an excluded atlas skips DWMWindow, an excluded part's ATLASRECT keeps the template sprite.

Windows 10 parts without a Windows 7 counterpart (dark glyphs, dark caption backgrounds, and the glow parts 92-94 that some DWM mods read) point at stock sprites in templates built from the Windows 7 atlas, so they follow the source's version of that sprite. A template that pairs a part with a different stock sprite than its name suggests keeps that pairing, with a warning.

Windows 7's frame highlights (LEFTHIGHLIGHTCORNER 34, SIDEHIGHLIGHT 43) have no Windows 10 consumer, and Windows 10 gave those ids to other parts. `PreserveHighlights` copies the source's records (ATLASRECT, IMAGECOUNT, SIZINGMARGINS, BGTYPE, per-state OPACITY) into the template's DWMWindow as parts 95 and 96 (`dwm-highlight-kept`), past every id uDWM asks for and next to the 92-94 glows. The output atlas starts with the source atlas at 0,0, so the rects stay valid; the validator checks the sprites pixel for pixel and accepts exactly these added records. A template that already has a part 95 or 96 keeps it and the highlight is skipped with a warning. OpenGlass's "From msstyles" highlight style reads these: Windows 7's uDWM (6.1.7762 `CTopLevelWindow::GetNCAreaHelper`, `CreateBitmapsFromAtlasImageStrip`) cut each rect into two tiles (active, inactive), read the corner's OPACITY per state pair and the side's OPACITY for states 1/2 plus its SIZINGMARGINS, and drew the right corner as the left one flipped.

### Part numbering across versions

The DWMWindow part table lives in uDWM, not uxtheme. Windows 7 has 71 parts. Windows 8.1 removed nine (BUTTONGLOW, LEFTHIGHLIGHTCORNER, the four FLIP3D parts, REFLECTIONMAP, SIDEHIGHLIGHT, SMALLBUTTONCLOSEGLOW) and renumbered everything after each gap, then added SQUEEGEEREFLECTIONMAP and THUMBNAILBORDER. Windows 10 1511 kept 1-64 and appended dark glyphs (65-88) and dark caption backgrounds (89-92). A later Windows 10 removed BUTTONCLOSEGLOW (11) and shifted every id from 12 down by one, so 19041 has dark glyphs at 64-87 and dark caption backgrounds at 88-91. That's why the importer matches by name and sprite, never by number. uDWM on every version aborts the whole theme load on the first part it asks for and doesn't find; from 8.1 on it also requires the DWMTouch, DWMPen, Animations and TimingFunction classes, so a Windows 7 style can't work on 8+ without a template.

## Parser fixes made along the way

- `PropertyStream.ReadNextProperty`: opaque (undecoded) payloads copied `data.Length - cursor` bytes into a `sizeInBytes` buffer, which throws for any record that isn't last. The load loop swallowed the exception without advancing, i.e. spun forever. Now copies exactly `sizeInBytes`, bounds-checked.
- The header scan could run past the end of the stream; it now stops and reports the skipped tail.
- `VisualStyle.LoadProperties` records every skipped or undecodable record in `LoadDiagnostics` instead of dropping it silently, and stops instead of spinning when the cursor can't advance.
- Records now step to the next 8-byte boundary when the gap is zero padding (uxtheme's `align8(32 + size)`). Before, the scan tolerated at most 4 skipped bytes, so a legal empty string (6 padding bytes) counted as damage.
- Nonzero bytes in the last 1-4 bytes of VARIANT are reported instead of ignored.
