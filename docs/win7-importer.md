# Win7 -> Win10 importer, developer notes

Code: `libmsstyle/Import/`. CLI: `msstyleImport/`. UI: `MainWindow.OnImportWin7Style` plus the result window `msstyleEditorSharp/Dialogs/Win7ImportDialog.cs`. Tests: `libmsstyleTests/Win7ImportTests.cs`. Tests that need a third-party Windows 7 style (not redistributable, so not in the repo) read its path from an environment variable and are inconclusive without it.

The base (stock Windows 7 aero) is `libmsstyleTests/styles/w7_aero.msstyles`, embedded into libmsstyle as `libmsstyle.Import.w7_aero.msstyles`. `StockStyles.Win7AeroPath()` writes it to `%TEMP%\msstyleEditor\w7_aero-<sha>.msstyles` because `VisualStyle.Load` goes through LoadLibraryEx. It has no .mui next to it, so base font/string properties can only be compared by id: a source that rewrote the text behind an unchanged id isn't detected (noted in every report).

In the editor the template is the open style: it's saved (standalone) to `%TEMP%\msstyleEditor-import\<time>\template\`, so unsaved edits count, the import writes `...\out\<name>-win7import.msstyles`, and on success that file replaces the open style. On failure the open style is left alone.

## Pipeline

1. `VisualStyle.Load` all three; any `LoadDiagnostics` entry blocks the run. Platform must be Vista/7 for source and base, 10/11 for the template.
2. `SemanticModel` flattens each style to `class|part name|S<state>|property#type[@n]`. Images compare by decoded pixels, string ids (FONT and non-image FILENAME) by their string-table text when both sides have a table, by id otherwise. Only IMAGEFILE..IMAGEFILE7/GLYPHIMAGEFILE are IMAGE references; resource ids use the low word like uxtheme. Numeric class ids never take part in matching.
3. `BuildThreeWayDiff` records every key (written to `<prefix>.threeway.json`).
4. `DwmImport` handles DWMWindow (below), then `MergeGenericClasses` everything else.
5. New bytes go through `ResourceIdAllocator` (max id + 1, shared when bytes are identical; ids with several language variants are never shared). Existing resources are never rewritten.
6. `VisualStyle.Save` into a validation folder of its own, with `StyleCompanions.CopyAlongside` putting the template's `Shell` folder and `<lang>\<name>.msstyles.mui` next to it (mui-based templates only resolve their string tables that way), then `StyleValidator` against the template. On success the file is moved to the output and the companions are copied there too; the validation folder is always deleted. The editor passes the opened file as `CompanionSourcePath`, because its template is a temp snapshot.

## Merge rules

- Three-way: source == base -> keep template; template == base -> take source; template == source -> nothing; otherwise keep template (`--prefer-source` overrides).
- Colors (type COLOR) always follow the source, over template adaptations too (`applied-color`). A color the source deletes is deleted from the output (`removed-color`, `RemovedRecords`). Other removals aren't imported. The validator accepts exactly the declared removals.
- A removal never empties a class, and an ordinary addition never gives an existing record-less class its first record: that shifts uxtheme's BCMAP registration indices. A class's last color instead gets the value the deletion falls back to (`pinned-color`). The explicit XP `ExplorerBar::Toolbar` addition is different: its class name is appended without changing existing CMAP bytes/IDs, and counted BCMAP entries and parents are relocated by actual registered class identity (record-bearing classes, then AMAP-only classes). The new class inherits Toolbar; validation independently preserves every old parent relationship and accepts only declared new map bytes/records. Extra font-size variants remap IDs by name plus duplicate occurrence and must share a compatible registration order.
- Records the source adds where stock Windows 7 has none (text glow on the address bar, a tree view font...) are added to the template (`added`, `TryAddRecord`) when the class exists there; a missing part/state section is created. The value goes through the same translation as any applied value.
- Template-only records that hide a value the source changed further up the inheritance chain get the source's value copied in, never deleted (`CopyIntoTemplateOverrides`, `copied-into-override`). Example: `Explorer::Button` doesn't exist on Windows 7, inherits `Button`, and adds its own PUSHBUTTON text colors that would otherwise beat the source's `Button` colors. Colors are copied in any class; other scalar types only in Windows 10-only classes. Pictures and strip geometry stay the template's. A Windows 10-only class also gets the source's other states of such a property where they differ from state 0 (`added-state-copy`), because Windows 10 falls back to the class's own state 0 there, not to the base class's state. `DarkMode*` classes are left alone: their dark backgrounds need the template's light text.
- Fonts are compared as parsed `FontSpec`s (grammar from uxtheme `_ParseFont`). A font the template has no string for is added to every string table with a fresh id and the candidate is saved standalone. The validator parses every font, checks all old strings still read the same and checks caption/small caption/menu fonts against their bar heights.

### Pictures and geometry

- Images that differ only by +-2 premultiplied rounding count as equal; templates often re-encode the stock images that way (real retouches differ by much more).
- When the template shows a stock picture that belongs to another part (e.g. a tab item drawn with the stock left-edge tab strip), the source's version of that other part is used (`FindImageAlias`, `applied-alias`).
- Strip geometry stays consistent: if IMAGECOUNT/IMAGELAYOUT/SIZINGMARGINS is a kept conflict, or the source changes one of them while some image of the part stays the template's, the whole part keeps the template geometry (`LockedGeometryParts`). Images on their own are decided one by one.
- A picture the template redrew (a conflict without a stock alias) takes the source's picture when the part ends up cut with the source's frame count, layout and margins (`GeometryIsSource`, `applied-picture-with-geometry`).
- Template-only dpi slots (IMAGEFILE1-7 the base doesn't have) don't lock a part. `FillDpiSlots` points them at the source's largest picture of the same state wherever the import replaced that state's pictures (`applied-dpi-fill`). Images both the source and the template added on top of stock follow the source in parts that take the source's geometry (`applied-with-geometry`).
- `PropagateImages` walks template images nobody touched (Windows 10-only classes, dark mode copies, extra dpi slots) that aren't still their own key's stock picture: a stock Windows 7 picture -> the source's version of it (`applied-stock-copy`), and an IMAGE id shared with an already replaced property -> the same replacement when all replacements of that id agree (`applied-shared-id`).
- XP sources only: Luna10 moved some stock pictures to another slot of the same part/state (TrayNotify buttons IMAGEFILE -> IMAGEFILE1, Combobox/Rebar chevron GLYPHIMAGEFILE -> IMAGEFILE1-7). `FollowMovedImages` gives such slots the source's version of the stock picture (`applied-moved-slot`).
- XP sources only: a geometry scalar the template retuned (SIZINGMARGINS) doesn't lock its part when every template picture there is still stock and the source replaced them; the source's numbers come with its pictures (TrayNotifyHoriz::TrayNotify).
- XP sources only: `GeometryIsSource` compares *effective* geometry. A missing IMAGECOUNT is one frame and a missing IMAGELAYOUT is the platform default (xp cuts strips horizontally, win10 vertically), so a template that dropped the layout record no longer hides a source picture behind "different geometry" (it was blocking Progress FILL/CHUNK: Pure's progress art stayed template's). A single-frame picture is compared by its frame count only: the orientation flag cuts nothing, so `XpStripRemap` skips one-frame states instead of reporting a "strip re-cut 1 horizontal -> 1 vertical" that never existed (that note used to appear for ExplorerBar's one-picture group parts and made them look skipped).
- XP sources only: `--prefer-source` also takes the source's *stock* value over a template adaptation for pictures and their strip geometry (`applied-stock-over-template`). Ordinary unchanged stock values keep the working port's adaptations. Explicit source ExplorerBar group/header values have precedence over stock shellstyle transcription; a shellstyle-specific override is translated only when genuinely distinct from the source style. Explicit header CONTENTMARGINS are not overwritten with template-relative shellstyle inset deltas.
- The Win10 task pane draws `dtb(ExplorerBar, ...)`, but that does not make explicit XP msstyles ExplorerBar artwork disposable. Group backgrounds, fonts and supported geometry follow the source style where present; shellstyle fills and layout-only adaptations remain a separate evidence level. `shellstyle-bitmaps-replaced: 0` counts only copied DLL bitmaps, not source art translated into msstyles records or markup changes. Final resource decisions must be checked against the same-run candidate/report, not a generic intermediate warning.
- XP shellstyle bitmaps are only copied into the win10 shellstyle under the ids both files share (folder watermarks 10-25, task pane art 100-112). Other coincident numbers are the win10 shellstyle's own graphics, referenced by its UIFILE (`graphic(id, 2, ...)`); substituting an xp picture there breaks Explorer's DirectUI parse at window creation (`DUIXMLParserFailure ... Unable to load graphics`, SevenVG RTM's id 121: a 200x551 xp task pane background in an 11x8 win10 glyph slot).
- XP shellstyle bitmaps drawn with `rcbmp(id, 2, ...)` (per-pixel alpha) follow DirectUI's rule (`convert.cpp` `HasAlphaChannel`): any non-zero alpha byte means the alpha channel is used, so 0/255-only bitmaps (TangoLux's task pane arrows) keep their transparent pixels. The uxtheme rule (alpha only counts when some pixel is partial) turned their background white.
- XP shellstyle (task pane) values are not read under fixed selectors. `DuiCascade` resolves what XP's DirectUI actually painted for each element, from shell32's own element tree (`shell32/folder.uix`: pane `sectionlist` > expando > header button > title / arrow, clipper > (watermark) > tasklist; `duitask.cpp`: task > button > title) and DirectUI's lookup rules from the XP source (`directui/engine/core/sheet.cpp`, `property.cpp`, `element.cpp`, GDI build `directui.lib` that shell32 links):
  - rules are per element class: an `element` rule matches plain Elements only, not Buttons or TaskLists;
  - the matching rule with the highest specificity wins: id conditions, then condition count, then the later rule;
  - no rule: `background`, `foreground`, `bordercolor` and the font properties inherit from the parent; `padding`, `margin` and `borderthickness` don't;
  - each expando carries `sectionss`/`mainsectionss` and each task `sectiontaskss`/`mainsectiontaskss` (`duiview.cpp`); `[selected]` and `[mousefocused]` come from the open section and the hovered button; `rcstr(n)`/`rcint(n)` read the shellstyle's own string table.

  The Windows 10 records are filled from those resolved values: header text = the header title's foreground (normal / hovered), task text = the task title's; the header picture = the first background an element from the title out to the expando sets itself, the group picture = the first one from the tasklist out to the expando. Bitmaps stay pictures (mode 6's keyed `rcbmp`, its transparent top band - the area XP's expando background covered - cut off since Windows 10 draws the header as a separate element; stretched with SIZINGMARGINS 0, as XP's own nine-grid was), solid colors become flat tiles, gradients (`gradient(c1, c2, mode)`, mode 0 horizontal / 1 vertical, render.cpp GradientFill) a stretched strip; the header button's and tasklist's own borders are drawn into them. An element whose background is only inherited paints nothing over its parent, so with no fill of its own the part is transparent and the pane shows through. A group fill that is the pane's gradient again counts as see-through too: on XP it can't be told from the pane (measured on Opus OS Blue at the same x inside and between groups), while a copy on Windows 10 would restart at each group's edge. Fonts: Windows 10 draws every header title with `TextStyle` BODYTITLE (`gtf(TextStyle, 3, 0)`) and every task link with HYPERLINKTEXT 0/2, so those get the resolved fontface/fontsize/fontweight/fontstyle (SHADED: "Swis721 Cn BT D-Type, 7, Bold" from its `rcstr(1)`/`rcint(15)`). Every value is resolved in stock Luna's shellstyle as well, and where the two agree the template's record stays, so stock Luna still ports to zero changes.
- XP shellstyle geometry, relative to stock Luna, whose layout the Luna port's records fit: `sectionlist` padding becomes ExplorerBar part 0 CONTENTMARGINS (`gtmar(ExplorerBar, 0, 0, 3602)`); the header button's borderthickness + padding difference moves NORMALGROUPHEAD/SPECIALGROUPHEAD CONTENTMARGINS (left, top, bottom); the tasklist padding difference moves NORMALGROUPBACKGROUND CONTENTMARGINS (`gtmar(ExplorerBar, 5, 0, 3602)`, every tasklist). Checked on a real XP: TangoLux's group header tops 7/121/255px in both; Opus OS Blue's header and task text start at the same x (13-14 / 40px) and the task pitch matches (22/19px).
- Two placements live in the Windows 10 shellstyle's own markup, not in any ExplorerBar record, so the porter edits the port's copy of the template shellstyle (`XpShellImport.PatchShellStyleLayout`, after the bitmaps):
  - Section gap: XP stacks expandos in a vertical flow layout using the larger of the two neighbouring margins (`verticalflowlayout.cpp`). Windows 10 pads each `Expando` at the bottom (`UIFILE 1`, `ExplorerBarStyle`, `rect(0,0,0,15rp)`). That padding moves by the source's gap minus stock Luna's 15rp. Opus OS 5rp, SHADED 10rp, Lion 0rp. Measured live with Opus OS Blue: the header rows went from 32/139/266 (XP 29/126/243) to 32/129/246, so each step is 97/117 as on XP.
  - Header title alignment: Windows 10 places the title button `layoutpos="left"` in a fill layout (`SHELL32_UIFILE`), so it sizes to its text. A centered or right-aligned source title (SHADED's `middlecenter`) loses `layoutpos` in every pane layout (fill layout `LP_Auto` stretches it over the header). Its `name_normal`/`name_special` button rule gets the source's `contentalign`, vertical part included (`middlecenter`, `topright`...): with `topcenter` SHADED's titles sat against the top edge of the header bar. The box it's aligned in is matched to XP's too. On XP the title is the header's border-layout client: inside the header's borderthickness + padding and the title's own padding, with the arrow (`layoutpos=right`, its bitmap width) taken off on the right. On Windows 10 it's the port's header CONTENTMARGINS, with the arrow overlapping. The name button's left/right padding evens out the difference. SHADED gets 10rp on the right; measured live, its title centers went from 5.5px right of the bar's center to 0.5px. A title padded out past its header (Lion's main section) isn't touched.
  - Task hover background (Lion OS X: `button [mousefocused] { background: rcbmp(110, 6, magenta) }` in its task sheets): Windows 10's DirectUI draws no shellstyle `rcbmp`/`resbmp` at all (tried live: nothing shows), only theme records through `dtb()`. So the picture becomes an ExplorerBar record on state 1 of the group background part (5 normal, 9 special; the UIFILEs only read state 0): IMAGEFILE, mode 6's nine-grid with the button's borderthickness as SIZINGMARGINS, key color see-through. The sheets then draw it. Place links are NavigateButtons, which never get MouseFocused, so they use a `mousewithin` rule. Their row's 5rp/2rp padding moves onto the link's icon and label, because a NavigateButton's own padding isn't applied. System Tasks rows (shell32 UIFILE 44, AJOSplitButton) get it with `mousewithin` too, and the ActionButton's own `dtb(CommandModule, 3, 2)` hover is cleared. Task lists become `verticalflowlayout(0,3,3)` and place rows `filllayout()`, so rows span the list's width as XP's did. Measured live: both kinds of bar now cover x 5-213 and are 19px tall. Sources without a hover background (stock Luna and the other ports) change nothing.
  - Pane background and folder watermark (CrystalBlue: `rcbmp(120, 5, ...)` on the sectionlist and a 24px watermark as its content picture): Windows 10's DirectUI draws neither a shellstyle's `rcbmp` nor a `sectionlist` content picture, so both become ExplorerBar records on spare states of part 0 (the UIFILEs read state 0 only): the pane picture on state 1, drawn unscaled (SIZINGTYPE TILE) from a copy padded with its own last column and row out to 210x1200rp (a nine-grid squeezes once the pane is shorter than its margins; a 420x2160 copy failed `SetSystemVisualStyle` with 0x8007000E), and the watermark on state 2. `ExplorerBarStyle` then swaps the pane's `ExplorerBarBackground` background from `gradient(gtc(ExplorerBar, 0, 0, 3810/3811))` to `dtb(ExplorerBar, 0, 1)`, and every `SHELL32_UIFILE` pane layout gets a `PaneWatermark` element as a `layoutpos="bottom"` child of the pane element at the picture's own height: inside the pane element's content padding (the source's `sectionlist` padding, `gtmar(ExplorerBar, 0, 0, 3602)`) the band spans exactly XP's content box, so the picture lands 1:1 where XP drew it.
  - The details section's text ("My Computer" / "System Folder" under the Details header): on xp those info lines (`NameSpaceItemInfoList`) draw no color of their own in themed mode and inherit system windowtext, and a theme overrides it in its shellstyle (CrystalBlue's `NameSpaceItemInfo { foreground: white }` over its dark group art; stock luna's sheet sets none). Windows 10 draws them through `genericlayoutstyle`'s `MetadataElement`/`MetadataLabel` rules, which read `PreviewPane`: 5/0 the title line, 6/0 the subtitle, 7/0 and 7/1 the metadata rows. The source's override (when it differs from stock luna's) becomes those `TEXTCOLOR` records; without one the template's black stays, as on xp. The detail markup's own `foreground` is no use: the `PreviewMetadata` module draws the text with the sheet's classes, not the element's property (tried live: still black).
  - Music and picture folder groups: `SHELL32_UIFILE` gives the special section in those folders its own background (`accname="music_bg"`/`"photo_bg"` -> `themeable(dtb(CommandModule, 11, 1/2), window)`, the template's light music/picture picture). xp drew those folders from the same section art as every other special group, and the light picture left the source's white group text invisible (CrystalBlue's Music Tasks body: white on white), so the two overrides are removed and ExplorerBar's group background shows.
  - Details section open from the start: its `Expando` in `SHELL32_UIFILE` is `Expanded="false"`, and Windows 10 then draws the section closed (title row only) until the info module has an item. xp always showed the folder's own name/type there, so the attribute becomes `Expanded="true"` (live: opening a folder from My Computer's My Documents link showed "Details" closed before, open after).
  - Color keys: `rcbmp(id, mode, key)` takes the explicit key for every mode but 2 (per-pixel alpha), not just mode 6. XtremeXP writes its arrows as `rcbmp(106,3,#FF00FF,...)`; reading only mode 6 painted them magenta inside a pink square.
  - Stylesheet comments: `/* *** TASK PANEL *** */` before a rule used to become part of the selector, and `DuiRule.Parse` dropped the rule. XtremeXP's whole `sectionlist` background was lost that way (the pane kept the template's blue gradient). Comments are stripped before rules are parsed, and a rule the element tree doesn't reach is also looked up by class/id in any sheet (`XpShellStyle.GetAny`), so a pack's rules keep resolving even when its sheets aren't the ones folder.ui names.
  - Unset geometry stays unset: a missing `padding` / `margin` the cascade can't resolve used to read as 0, which pulled XtremeXP's task lists out to the group edge and collapsed its section gap to 0rp. A null now means "the source doesn't state it", so the template's inset and spacing stay.
  - Address bar band: XP's `Rebar|BAND` state 0 is see-through (`TRANSPARENT` true, no fill of its own), so the rebar background picture (`Rebar` part 0 `IMAGEFILE`, XtremeXP's ribbed strip) shows through it. Windows 10 fills the band's own box from its `BGTYPE 2` fill instead, which left the address row flat where XP had the picture. The porter now copies the rebar background's picture and geometry (`BGTYPE 0`, `IMAGEFILE`, `IMAGECOUNT 1`, `IMAGELAYOUT`, `SIZINGTYPE`, `SIZINGMARGINS`, `TRANSPARENT`, `TRANSPARENTCOLOR`) onto `Rebar|BAND` state 0 for a see-through band.
  - A template without these attributes is left alone, with a warning in the report.
- XP sources only: a part whose every stock picture the source replaced is cut with the source's geometry, even where the template retuned a number there. The template fitted that number to its own redrawn art, which won't be shown (`SourceReplacedEveryPicture`). Lion's TrackBar THUMBBOTTOM showed Luna's slider thumb because Luna10 moved its SIZINGMARGINS.
- XP sources only: a BGTYPE the source changed but the template never had is added. uxtheme defaults a missing BGTYPE to BORDERFILL, which ignores the IMAGEFILE that does come over (TangoLux's address box lost its frame on Luna10's plain Combobox).
- XP sources only: IMAGELAYOUT/IMAGECOUNT records the template doesn't have are added from the source, and the strip-fit check uses the source's layout there. A missing IMAGELAYOUT is horizontal on XP but vertical on Windows 10, so Lion OS X's three side-by-side `TrayNotifyVert` tray frames (Luna10 dropped that part's layout) were rejected as "doesn't split into 3 vertical frames" and Luna's tray picture stayed.
- XP sources without `Shell\<scheme>\shellstyle.dll` (Flarn): XP's shell32 (`SHGetShellStyleHInstance`) falls back to `%SystemRoot%\System32\shellstyle.dll`, the classic stylesheet written in system color names (`window`, `buttonface`, `activecaption`...). That file (from XP x64 SP2, embedded as `xp_classic_shell.dll`) becomes the source shellstyle, its color names resolved with the theme's own SysMetrics (uxtheme's `DefaultColors` where the theme leaves one out). Measured on XP x64 SP2 under Flarn: the special group (System Tasks) is drawn like the other groups (buttonface header, buttontext), not activecaption as the stylesheet reads, so it takes the normal section's header/tile. Color headers become flat 10x10 tiles; bare `rcbmp(id)` arrows are color-keyed on their top-left pixel (DirectUI `GRAPHIC_TransColor` with an automatic key).
- XP sources only: an image glyph (`GLYPHIMAGEFILE`) is re-cut with the same frame map as its part's strip (Toolbar SPLITBUTTONDROPDOWN 6 -> 8), and the template's glyph dpi slots (IMAGEFILE1-7 of a part with GLYPHTYPE=IMAGEGLYPH and an IMAGESELECTTYPE) take the source's glyph, not its background strip. The back/forward dropdown arrows were missing before.
- The validator wants every changed strip image to divide into its effective IMAGECOUNT, except where the source ships that exact picture with that count: Windows 7 drew those and no uxtheme check rejecting a remainder was found, so they're warnings (`CollectFrameWaivers`). XP sources whose strip has the same count and layout as the target property are applied despite a remainder (uxtheme slices `length / count` on XP and Windows 10 alike) and get the same waiver: appows' 53px frame borders with ImageCount 2.
- XP bitmaps: a 16/24/32bpp DIB can still carry `biClrUsed` palette entries; the pixels start after them (GDI skips them). Reading from right after the header turned appows' separators and tree glyphs into palette garbage.
- XP strip re-cuts (`XpStripRemap.LearnMap`): a stock frame is a candidate for template frame j only if it matches in every comparable image of the state (background and glyph strips). Stock ScrollBar ARROWBTN backgrounds are identical for all directions, so the background alone mapped the down/left/right hover frames to "up"; the glyph strip disambiguates. Among candidates j itself wins. A part the template redrew takes the map of the part it's drawn on (ScrollBar GRIPPERHORZ/VERT <- THUMBBTNHORZ/VERT); Luna10's grippers are blue art.
- XP strip re-cuts where Luna10 also changed the frame size (Header HEADERITEM: 5 frames of 18x18 -> 12 of 18x20; ScrollBar ARROWBTN 15px -> 17px): stock frames are compared scaled to the template's frame size, and the re-cut stock is scaled the same way. The source's art keeps its own frame size; uxtheme stretches it by SIZINGMARGINS as XP did. Scaling it duplicated the middle row/column, which is where an arrow glyph sits (Flarn's scroll arrows came out fat).
- Strips where win10 added states xp never drew (Button CHECKBOX: 12 -> 20 frames, the last four are "excluded"): when at least three quarters of the template frames match stock, the rest take their closest stock frame (reported). The re-cut stock then becomes the template's own strip, so the importer sees stock the template left alone and the source's art replaces it, including the dpi slots Luna10 rescaled (CheckBox25 -> 20px). Before, Luna10's white boxes stayed under GSM.
- XP resize grips: `Status` GRIPPER (part 3) and `ScrollBar` SIZEBOX (part 10) are separate consumers. When the template redrew their strips and pixel mapping cannot recover stock frames, custom one/two-frame XP art is expanded into the template's eight alignment states before `SingleImageIntoDpiSlots` fills IMAGEFILE1–7. Keep each consumer's own art, native frame dimensions, and coherent IMAGECOUNT/IMAGELAYOUT. States are right/left, top-right/top-left, then their half counterparts: retain both original right/left frames (reflect one-frame art horizontally for left), reflect top variants vertically, and repeat the corresponding full motifs for half states as the template does. These are alignment states, not normal/pressed frames. Stock XP art is not refitted, so stock template adaptations remain unchanged. Do not enlarge true-size grips to Luna's dimensions or bypass the strip-fit safety gate.
- XP sources: ListView/TreeView/ListBox with a non-white BORDERFILL get SIZINGBORDERWIDTH 2. comctl32 `CCDrawNonClientTheme` (cutils.c) draws a client edge with the theme background, then fills what a BORDERSIZE thinner than the 2px edge leaves with the control's brush, which is white for Task Manager's, the Open dialog's and WinForms lists: a 1px white ring inside GSM's dark border.
- XP sources: Spin UP/DOWN/UPHORZ/DOWNHORZ pictures with transparent pixels are flattened onto the source's BTNFACE. comctl32's up-down erases with BTNFACE (updown.c class brush) before drawing them; WinForms' NumericUpDown buttons (`UpDownButtons`, `ControlStyles.Opaque`) don't, and GSM's fully see-through button backgrounds showed white.
- XP sources: a single source strip frame (GSM's shafts) is repeated into every template frame; a source strip with stock's frame count but the other layout (GSM's horizontal thumb strip) is cut in its own layout and mapped like stock.
- XP sources: one IMAGEFILE where the template picks its picture from IMAGEFILE1-7 (IMAGESELECTTYPE set) fills those slots (`SingleImageIntoDpiSlots`); uxtheme never reads IMAGEFILE there. `Explorer::TreeView` GLYPH/HOTGLYPH (no `TreeView` inheritance) take `TreeView` GLYPH: GSM's +/- boxes.
- XP sources: a COLOR the source changed that the template dropped is added (Luna10's Combobox has no FILLCOLOR; GSM's address box was white).
- XP sources whose `Combobox` common properties are an IMAGEFILE plate instead of a BORDERFILL: the plate's edge and face colors are sampled onto the BORDERCOLOR/FILLCOLOR win10 draws the frame with (`FrameXpCombo`). win10 draws Combobox|4 BORDER as a border fill and never that plate, so the source's *no-picture* fallback colors — the pair XP uses only when the plate is missing (Elfin2: 0,0,0 edge and 140,140,140 face) — painted a black box with a dark grey face on the address bar.
- XP sources whose combo button is one picture with no glyph of its own (an empty or missing GLYPHIMAGEFILE): the template's dpi glyph selection is turned off (`DropGlyphlessXpButtonDpi`, `dropped-xp-button-dpi`), so uxtheme draws the source's strip at the source's SIZINGTYPE. Otherwise it re-cut the strip as a dpi glyph — Elfin2's 10x10 arrow came out as a broken chevron almost twice its size. `SizingTypeFromXp` also maps win10's right-to-left mirrors (DROPDOWNBUTTONRIGHT/LEFT) back to XP's one DROPDOWNBUTTON, since a style needn't declare the mirrored part ids.
- XP sources: `Window` CONTENTALIGNMENT the template dropped is added when the source doesn't leave it left (NOOTOR GTK, Xanadu centre their titles). win10 reads CONTENTALIGNMENT with a left default and Luna10 kept that record only for MAXCAPTION, as 0, so a centred style's maximized caption fell back to left while its normal caption stayed centered.
- XP captions use STRETCH on Win10 without replacing one caption part's artwork/geometry with another's (`StretchXpMaxCaption`, `applied-caption-stretch`). MAXCAPTION is part 5 on both platforms. Normal caption art may deliberately have transparent top rows; copying it over the separate maximized art exposes the desktop. Keep source caption heights and margins; do not pad the picture or substitute stock XP (the three-way `m_base`, **not** the Win10 template) metrics/frame hints.
- XP sources: template pictures painting an area XP filled with a color become a borderless BORDERFILL in that color when the source changed it (`FillFlatFromXp`): Edit BACKGROUND <- Edit EDITTEXT FILLCOLOR (win10's themed edit paints EP_BACKGROUND first; the address bar and text boxes stayed white), PreviewPane NAVPANESIZER/READINGPANESIZER <- system BTNFACE (Luna10's beige 3px pane splitter).
- XP sources: a rebar backdrop shipped one pixel wide (a 1xN column of fixed edge rows and a stretchable fill row) is widened to the template picture's **width**, retaining the source **height**, every source row and the source's valid SIZINGMARGINS (`RebuildBandPicture`, `BandMarginsForRebuiltPictures`). Resampling to the template height loses gradients and thickens separator lines. ## Color and size variants (XP)

uxtheme 19041, observed with `LoaderLoadTheme`/`EnumThemeColors`/`EnumThemeSize`/`GetThemeDocumentationProperty` on hand-edited copies of Luna10:

- `VMAP`: (VARIANT resource name, size name, color name) triples; each string is an int32 wchar count (terminator included) and the wchars, padded to 8 bytes. `LoaderLoadTheme(color, size)` picks the VARIANT resource of the matching triple (E_INVALIDARG for an unknown pair).
- `EnumThemeSize`/`EnumThemeColors(index)` walk the CMAP classes named `sizevariant.X` / `colorvariant.X` in CMAP order; the name is X, an index whose class has no VMAP triple fails (Luna10's `sizevariant.Default` is index 1, so a size added after it is index 2). Callers must skip failed indices.
- `RMAP`: 32-byte records (name id, type 201, class index, part, state, string id, 0, inline byte count) with an inline UTF-16 string or a string table id. 601 = display name, 602 = tooltip; class 0 (`documentation`) 601 is the theme's DisplayName.
- Records of a variant class are never needed; added classes go to the end of CMAP (no VARIANT class index moves) with a `-1` BCMAP entry.

`XpThemeImport` writes Luna/Olive/Silver's layout: one folder per theme, one `.msstyles` per color scheme named after the scheme, `Shell\<scheme>` next to it (Windows loads `Shell\<ColorName>\shellstyle.dll`; checked: Green loads `Shell\Green`). Each other XP size (`[File.X] Sizes = LargeFonts`) is ported on its own from the same template (`Win7ImportOptions.SourceSize`) and merged by `VariantWriter` as VARIANT `S_<SIZE>`: its IMAGE/STREAM resources and font strings are matched to the main file by content, new ones get fresh ids. The color variant is renamed to the scheme (`colorvariant.Green`, display name "Green") and the documentation name becomes the XP theme's. Every color/size pair is then loaded through uxtheme (`UxthemeLoader`); a failure blocks the scheme.

Names come from the packed XP style's string table, which is what XP itself showed (themeldr `tmutils.cpp` `_EnumThemeColors`/`_EnumThemeSizes`, `GetThemeDocumentationProperty`), not from THEMES_INI's `DisplayName` lines: color i = string 1000+i and size i = 3000+i (i = index in the `COLORNAMES`/`SIZENAMES` resources), theme name = 5000. Authors set these freely: Flarn's sizes are "HaxrCorp S8 / Tahoma / Trebuchet MS", appows' "segoe ui / corbel / arial", minus4's "[01/03] default ...". The default size's name goes onto the template's `sizevariant.NormalSize` class.

Color schemes come from packthem's tables, which is what XP loads: COMBODATA (`cColors, cSizes`, then the file number of every color/size pair, -1 = none; themeldr `tmutils.cpp` COMBOENTRY) indexes FILERESNAMES, COLORNAMES/SIZENAMES name them. THEMES_INI only supplies display names, and is only parsed for schemes when a style has no COMBODATA. Its `[File.X] ColorSchemes` lines can name schemes that don't exist: Lion OS X has `[ColorScheme.NormalColor]` but every file says `ColorSchemes = Lion`, which packthem resolved when it built the tables ("No color schemes found in THEMES_INI!" before).

deskn.cpl (`deskcpl`, AppearancePage.cpp), matched to XP's themeui (`nt5src/.../shell/themes/themeui/baseappearpg.cpp`): every folder directly in `Resources\Themes` is a "Windows and buttons" entry, labelled with its styles' documentation DisplayName (XP `CSkinScheme::get_DisplayName`); colors and sizes show EnumThemeColors/EnumThemeSizes `szDisplayName` as is (Luna/Olive/Silver keep their localized names). Apply with a size goes straight to `SetSystemVisualStyle(path, color, size)` with metrics built from that variant (Theme Manager ignores sizes). After every msstyle apply deskn sets and persists the style's 31 system colors, as XP's uxtheme did (`loader.cpp` SetSystemMetrics: `SetSysColors(TM_COLORCOUNT)` + `PersistSystemColors`); Windows 10 doesn't, and GSM "three" ran with the previous scheme's palette.

Install & apply (editor, `XpImportDialog.Install`): the port's folder and `.theme` are copied to `%WINDIR%\Resources\Themes` (an elevated `cmd` script renames the folder that is already there to `<name>.old-<stamp>` first: renaming works even while the applied style's files are memory-mapped, while robocopy over them silently left a half-copied install). The apply itself is in-process (`libmsstyle.Import.XpThemeApply`, also `msstyleImport apply-theme <theme>`): the shell handler `themecpl.dll,OpenThemeAction` (the `.theme` "open" verb) does apply everything, but it opens Settings while it does and a rundll32 started from an already-elevated process just exits without applying, so it is not used. Instead:
- the style goes through uxtheme's `SetSystemVisualStyle` (`#65`, the call the editor previews with), then a 500 ms wait: Windows swaps the style on its own thread and would clobber metrics/colors set too early;
- the style's `sysmetrics` class supplies what themeui copies into the session: the 31 system colors (`SetSysColors` + `HKCU\Control Panel\Colors`), the ten sizes and six fonts (`SPI_SETNONCLIENTMETRICS`, persisted as `WindowMetrics\<Name>` twips and the font blobs, `SPI_SETICONTITLELOGFONT`) and flat menus — this is why applying an XP port resizes captions/menus even when its `.theme` has no `[Metrics]`;
- the `.theme`'s own `[Metrics]` ANSI blobs (`NonclientMetrics` 340 bytes, `IconMetrics` 76) are converted to the wide structs Windows 10 expects (504/108) and applied/persisted on top;
- colors last (metrics broadcast `WM_SETTINGCHANGE`), desktop picture/fit/screensaver, cursors (`SPI_SETCURSORS`), sound events (`HKCU\AppEvents\Schemes\...\.Current`) and per-CLSID default icons (`HKCU\...\Explorer\CLSID`), then `Themes\CurrentTheme` = the installed file;
- every step is reported (notes and warnings) and ok means the style was accepted and `ThemeManager\DllName` named the installed `.msstyles`, so a half-applied theme is visible instead of silent.

## DWMWindow

For XP input, `Window` CAPTION/FRAMELEFT/FRAMERIGHT/FRAMEBOTTOM and their small counterparts are rasterized into the target's existing frame/squeegee/no-shadow slots. XP caption-button background and selected-DPI glyph layers are mapped separately, with source active/inactive states, color-key transparency and fitted nine-grid margins. Atlas dimensions, rectangle contracts, frame counts and unrelated sprites remain the target's; sprite validation records the exact expected replacement pixels. Source image content is therefore not replaced by a stock Luna frame merely because XP lacks `DWMWindow`.

The XP adapter reports representational limits explicitly: several buttons share one generic target face; the target's four-state glyph strip has no independent inactive glyph strip; font glyphs cannot be copied as nonexistent bitmap pixels; overlapping atlas consumers must agree. Native compositor placement, shadows and maximized-window geometry remain OS behavior rather than a promise of XP 1:1. The following stock-atlas matching rules apply to Windows 7 input, not to this XP synthesis path.

The template atlas has to be the stock Windows 7 atlas (pixel-compared, `TemplateAtlasIsStockWin7`). Then:

- a template rect equal to the stock rect of the same-named Windows 7 part maps by name;
- otherwise the rect is looked up among stock Windows 7 rects (alias). Several Windows 7 parts may share one stock rect; that's only followed if the source gave all of them the same pixels (`ChooseAlias`);
- anything else keeps the template sprite, copied into a strip below the source atlas (`fallback`), and the part keeps its template properties.

A mapped part takes the source sprite at whatever size it has, plus the numbers that describe it (IMAGECOUNT, SIZINGMARGINS, CONTENTMARGINS, `applied-with-sprite`), even where the template had adapted them: those belonged to the template's sprite. The fallback is only for sprites that can't be traced, or parts excluded by rule.

`CheckGeometry` then only warns (`GeometryWaivers`, `dwm-geometry-warning`). Strips are taken as sliced proportionally like the editor slices them (uDWM's rounding isn't verified), so odd sizes are fine; what gets a warning is a strip with nothing left after uDWM's 1px inset, or margins wider than the strip. Exclude rules work here too: an excluded atlas skips DWMWindow, an excluded part's ATLASRECT keeps the template sprite.

Windows 10 parts without a Windows 7 counterpart (dark glyphs, dark caption backgrounds, and the glow parts 92-94 that some DWM mods read) point at stock sprites in templates built from the Windows 7 atlas, so they follow the source's version of that sprite. A template that pairs a part with a different stock sprite than its name suggests keeps that pairing, with a warning.

Windows 7's frame highlights (LEFTHIGHLIGHTCORNER 34, SIDEHIGHLIGHT 43) have no Windows 10 consumer, and Windows 10 gave those ids to other parts. `PreserveHighlights` copies the source's records (ATLASRECT, IMAGECOUNT, SIZINGMARGINS, BGTYPE, per-state OPACITY) into the template's DWMWindow as parts 95 and 96 (`dwm-highlight-kept`), past every id uDWM asks for and next to the 92-94 glows. The output atlas starts with the source atlas at 0,0, so the rects stay valid; the validator checks the sprites pixel for pixel and accepts exactly these added records. A template that already has a part 95 or 96 keeps it and the highlight is skipped with a warning. OpenGlass's "From msstyles" highlight style reads these: Windows 7's uDWM (6.1.7762 `CTopLevelWindow::GetNCAreaHelper`, `CreateBitmapsFromAtlasImageStrip`) cut each rect into two tiles (active, inactive), read the corner's OPACITY per state pair and the side's OPACITY for states 1/2 plus its SIZINGMARGINS, and drew the right corner as the left one flipped.

### Part numbering across versions

The DWMWindow part table lives in uDWM, not uxtheme. Windows 7 has 71 parts. Windows 8.1 removed nine (BUTTONGLOW, LEFTHIGHLIGHTCORNER, the four FLIP3D parts, REFLECTIONMAP, SIDEHIGHLIGHT, SMALLBUTTONCLOSEGLOW) and renumbered everything after each gap, then added SQUEEGEEREFLECTIONMAP and THUMBNAILBORDER. A later Windows 10 removed BUTTONCLOSEGLOW (11) and shifted every id from 12 down by one, so 19041 has dark glyphs at 64-87 and dark caption backgrounds at 88-91. ## Parser fixes made along the way

- `PropertyStream.ReadNextProperty`: opaque (undecoded) payloads copied `data.Length - cursor` bytes into a `sizeInBytes` buffer, which throws for any record that isn't last. The load loop swallowed the exception without advancing, i.e. spun forever. Now copies exactly `sizeInBytes`, bounds-checked.
- The header scan could run past the end of the stream; it now stops and reports the skipped tail.
- `VisualStyle.LoadProperties` records every skipped or undecodable record in `LoadDiagnostics` instead of dropping it silently, and stops instead of spinning when the cursor can't advance.
- Records now step to the next 8-byte boundary when the gap is zero padding (uxtheme's `align8(32 + size)`). Before, the scan tolerated at most 4 skipped bytes, so a legal empty string (6 padding bytes) counted as damage.
- Nonzero bytes in the last 1-4 bytes of VARIANT are reported instead of ignored.

## Fix-all audit integration and native evidence (2026-11-11)

`BUGTOFIX.md`'s port11 ledger enumerates both audits, including stale-artifact claims and intentional adaptations. Treat one generation's JSON, style and validation as a unit: older `inv-now.tsv` / `inv-seven-out.tsv` dumps are not current installed inventories. An initial merge decision is not necessarily the last writer; shellstyle and specialized geometry passes run afterward.

Shell translation statistics are document-scoped, not a global unsupported-rule tally. Identical stock rules, specialized bitmap/inset/font imports, actual declarations mapped to existing consumer elements, and genuinely absent XP structures are counted separately. A category rule can have no target in UIFILE 1 yet map into the independently hosted `CategoryPanelStyle` in `SHELL32_UIFILE 24`; a warning for the former does not negate the latter. No XP scrollbar/blockade/accent/container tree is fabricated: native scrollbar artwork belongs to msstyles, and changed structural rules without a real Win10 consumer remain explicit limitations.

`tools/FidelityProbe.cs` is a retained C#/.NET Framework native diagnostic, compiled x64 against `libmsstyle.dll`, `System.Drawing.dll` and `System.Windows.Forms.dll`. Arguments are `<evidence-directory> <previous.msstyles> <current.msstyles> <source-xp.msstyles> [source-scheme] [--offline-only]`. It compares decoded artwork and geometry for rebar, menu, headers and CommandModule, records Start pane sizes and ExplorerBar properties, draws native parts at 96/144/192 DPI, captures real push/radio/check/combo/spin/trackbar/status controls with active and inactive captions, records the active theme and DWM composition status, and captures/measures existing Explorer and classic Start control trees. It does not apply themes, modify Windhawk, or alter shell configuration. PrintWindow output is retained evidence, not an aesthetic success assertion.

Evidence levels remain separate: matching source pixels in an output resource proves import fidelity; successful `DrawThemeBackground` proves the native API can paint that part; an actual control rectangle and capture prove that surface exists. Neither a successful draw nor an uninspected screenshot establishes visual 1:1 equivalence. In particular a native CommandModule draw does not prove a FolderBandModule is instantiated in every Explorer layout, and a DWM atlas sprite does not prove an unavailable compositor feature is enabled.

Reinstallation on this machine must release both the mapped style and its shellstyle: apply installed `LunaRef.theme` with `apply-theme --style-only`, stop Explorer, replace the generated style folder and theme files, restart Explorer, then apply the updated SevenVG theme style-only. This preserves the user's existing shell configuration and avoids the previously observed full-apply broadcast hang. Style-only does not reapply system colors, metrics, wallpaper, cursor/sound/icon registry extras; record that distinction explicitly rather than claiming the entire `.theme` was applied.

XP desktop system icons must come from the original XP binaries, not the same indices in Windows 10's shell libraries. Pack-shipped icons retain priority. For XP system references, supply original `explorer.exe`, `mydocs.dll` and `shell32.dll` in `XP_THEME_SYSTEM_ASSETS`, or an `xp-system-assets` directory above the source theme. Missing originals are reported as unresolved; no Win10 `imageres.dll` substitution is presented as XP artwork. Source-absent metrics/cursors remain absent instead of inventing assets.

For a safe style-only reinstall followed by the generated theme's explicit icon/mode values, run `msstyleImport apply-theme <installed.theme> --appearance-only`. This supported selective path uses the same icon override tracking as full apply and writes only `AppsUseLightTheme`/`SystemUsesLightTheme` for explicit valid `AppMode`/`SystemMode` entries, with read-back and a bounded immersive-color notification. It does not reapply the style, palette, metrics, wallpaper, cursors, sounds or current-theme selection. Do not combine it with `--style-only`. Capture prior per-CLSID icon overrides and Personalize values before applying when retaining native installation evidence.
